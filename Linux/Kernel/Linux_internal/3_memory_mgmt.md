# Chapter 3 – Linux Memory Management

---

# 1. Why Memory Management Matters

A Linux process does not directly work with physical RAM.

Instead, it works with **virtual addresses**.

Linux and the CPU translate:

```text
Virtual Address
      |
      v
Page Tables
      |
      v
Physical Address
      |
      v
RAM
```

This provides:

* Process isolation
* Efficient memory allocation
* Virtual memory
* Memory sharing
* Demand paging
* Copy-on-Write
* Memory-mapped files
* Shared libraries
* Memory protection

---

# 2. Virtual Memory

Each process gets its own virtual address space.

Conceptually:

```text
Process A

Virtual Address Space
        |
        v
   Page Tables
        |
        v
Physical RAM
```

Another process has a different virtual address space:

```text
Process B

Virtual Address Space
        |
        v
   Page Tables
        |
        v
Physical RAM
```

Therefore:

```text
Process A virtual address 0x1000
```

and:

```text
Process B virtual address 0x1000
```

can refer to completely different physical memory.

---

# 3. Why Virtual Memory?

Virtual memory provides several important benefits.

## Isolation

One process cannot normally access another process's memory.

```text
Process A
   X
Process B memory
```

## Protection

Pages can be marked:

```text
Read
Write
Execute
```

## Memory Overcommit

Processes can have virtual memory larger than currently available physical RAM.

## Sharing

Different processes can intentionally map the same physical pages.

## Simpler Programming Model

Each process sees a private address space.

---

# 4. Virtual Address vs Physical Address

A virtual address is generated by the CPU while executing a process.

A physical address identifies a location in RAM.

Example:

```text
Virtual Address
0x7fff12345000
       |
       v
MMU
       |
       v
Physical Address
0x12345000
```

The translation is performed using page tables.

---

# 5. MMU

The **Memory Management Unit (MMU)** is hardware responsible for translating virtual addresses into physical addresses.

Conceptually:

```text
CPU
 |
 | Virtual Address
 v
MMU
 |
 | Page Table Lookup
 v
Physical Address
 |
 v
RAM
```

The Linux kernel manages the page tables, while the CPU/MMU performs the actual translation during memory access.

---

# 6. Pages

Linux manages memory primarily in units called:

```text
Pages
```

A common page size is:

```text
4 KB
```

But architectures can support other page sizes.

Example:

```text
Physical RAM

+--------+--------+--------+--------+
| Page 0 | Page 1 | Page 2 | Page 3 |
+--------+--------+--------+--------+
```

Memory management operates heavily at page granularity.

---

# 7. Page Size

Suppose:

```text
Page size = 4096 bytes
```

Then:

```text
1 page = 4 KB
```

A 16 KB allocation requires at least:

```text
4 pages
```

if allocated page-by-page.

Linux also provides higher-level allocators for smaller objects.

---

# 8. Page Number and Offset

A virtual address can conceptually be divided into:

```text
+----------------------+------------+
| Page Number          | Offset     |
+----------------------+------------+
```

For a 4 KB page:

```text
4 KB = 4096 = 2^12
```

Therefore:

```text
Offset = lower 12 bits
```

The remaining bits identify the virtual page.

Example:

```text
Virtual Address
+----------------------+------------+
| Virtual Page Number  | Offset     |
+----------------------+------------+
                         12 bits
```

---

# 9. Page Table

A page table maps virtual pages to physical pages.

Conceptually:

```text
Virtual Page       Physical Page

0x1000 ----------> 0xA000
0x2000 ----------> 0xC000
0x3000 ----------> 0x5000
```

Therefore:

```text
Virtual Address
      |
      v
Page Table
      |
      v
Physical Page
```

---

# 10. Page Table Hierarchy

Modern CPUs generally use multi-level page tables.

Conceptually:

```text
Virtual Address
      |
      v
+-----------+
| Level 4   |
+-----------+
      |
      v
+-----------+
| Level 3   |
+-----------+
      |
      v
+-----------+
| Level 2   |
+-----------+
      |
      v
+-----------+
| Level 1   |
+-----------+
      |
      v
Physical Page
```

The exact number and names of levels depend on architecture and configuration.

For example, x86-64 uses a multi-level page-table structure.

---

# 11. Why Multi-Level Page Tables?

A flat page table could be extremely large.

Suppose a process has a huge virtual address space but only uses a small portion.

A flat table would waste memory.

Multi-level tables allow Linux to allocate page-table structures only for regions that are actually used.

Conceptually:

```text
Huge Virtual Address Space
        |
        v
Only used regions
        |
        v
Page-table structures
```

---

# 12. TLB

Page-table lookups are expensive if performed for every memory access.

Therefore CPUs use a cache called:

```text
TLB
```

Translation Lookaside Buffer.

It caches recent virtual-to-physical translations.

```text
CPU
 |
 | Virtual Address
 v
TLB
 |
 +-- Hit --> Physical Address
 |
 +-- Miss
      |
      v
  Page Table
      |
      v
Physical Address
```

---

# 13. TLB Hit

Suppose:

```text
Virtual Page 100
```

is already in the TLB.

Then:

```text
Virtual Address
      |
      v
     TLB
      |
      v
Physical Address
```

This is fast.

---

# 14. TLB Miss

If translation is not in the TLB:

```text
Virtual Address
      |
      v
TLB Miss
      |
      v
Page Table Walk
      |
      v
Physical Address
```

The translation can then be cached in the TLB.

---

# 15. Why TLB Matters

For every normal memory access, address translation is required.

Therefore:

```text
Good TLB locality
      |
      v
Better performance
```

while:

```text
TLB misses
      |
      v
Additional translation overhead
```

This is particularly important in:

* Databases
* Networking
* High-performance computing
* Storage
* Large-memory systems

---

# 16. Page Fault

A page fault occurs when a process accesses a virtual address that requires kernel handling.

Not every page fault means an error.

For example:

```text
Valid demand-paged memory
        |
        v
Page Fault
        |
        v
Kernel loads/creates page
        |
        v
Execution continues
```

This is a **minor/normal memory-management event**, not necessarily a crash.

---

# 17. Page Fault Example

Suppose:

```c
char *p = malloc(4096);

*p = 'A';
```

The virtual memory may have been reserved/mapped without a physical page being immediately populated.

When the CPU accesses the page:

```text
Memory Access
     |
     v
Page not currently mapped as required
     |
     v
Page Fault
     |
     v
Kernel
     |
     v
Prepare physical page
     |
     v
Update page table
     |
     v
Retry instruction
```

---

# 18. Major vs Minor Page Fault

Page faults can broadly be classified as:

## Minor Page Fault

No disk I/O is required.

Examples include cases where the kernel can satisfy the fault using already available memory or mappings.

## Major Page Fault

Disk/storage I/O is required.

Example:

```text
Process
   |
   v
Page Fault
   |
   v
Page not in RAM
   |
   v
Read from storage
   |
   v
Map page
```

Major page faults are significantly more expensive.

---

# 19. Demand Paging

Linux can load memory pages only when they are actually needed.

This is:

```text
Demand Paging
```

Instead of:

```text
Load everything immediately
```

Linux can do:

```text
Use page
   |
   v
Fault
   |
   v
Bring/create page
```

Benefits:

* Faster startup
* Lower memory usage
* Efficient memory utilization

---

# 20. Copy-on-Write and Memory

COW is not limited to `fork()` conceptually.

It allows multiple mappings to share physical pages until modification.

Example:

```text
Process A ----+
              |
              v
          Physical Page
              ^
              |
Process B ----+
```

When Process B writes:

```text
Process A ---> Page A

Process B ---> Page B
```

This reduces unnecessary copying.

# 22. Text Segment

The text segment contains executable instructions.

Conceptually:

```text
+------------------+
| Machine Code     |
+------------------+
```

It is normally:

```text
Readable
Executable
Not writable
```

This helps prevent accidental modification of program code.

# 23. Data Segment

Initialized global and static variables reside in the data region.

Example:

```c
int global = 10;
static int count = 5;
```

Conceptually:

```text
+------------------+
| Initialized Data |
+------------------+
```

---

# 24. BSS

BSS contains zero-initialized or uninitialized global/static variables.

Example:

```c
int global_array[1000];
static int count;
```

Conceptually:

```text
+------------------+
| BSS              |
+------------------+
```

The executable does not need to store all zero bytes explicitly.

---

# 25. Heap

The heap is used for dynamic memory allocation.

Example:

```c
int *p = malloc(sizeof(int));
```

Conceptually:

```text
Heap
 |
 +---- malloc()
 |
 +---- malloc()
 |
 +---- free()
```

The C library allocator manages user-space allocations.

The kernel ultimately provides/manages the underlying virtual memory mappings and physical memory.

---

# 26. Stack

The stack is used for:

* Function calls
* Local variables
* Return addresses
* Function parameters
* Saved execution state

Example:

```c
void foo()
{
    int x = 10;
}
```

Conceptually:

```text
Stack
 |
 +-- foo()
      |
      +-- x
```

The stack normally grows toward lower addresses on common architectures, but this is architecture-dependent.

---

# 27. mmap()

`mmap()` maps memory or files into a process's virtual address space.

Example:

```c
void *p = mmap(...);
```

Conceptually:

```text
Process Address Space
        |
        +-- mmap()
              |
              +-- Anonymous Memory
              |
              +-- File Mapping
```

`mmap()` is extremely important in Linux.

---

# 28. Why mmap() Is Important

`mmap()` is used for:

* Memory allocation
* Shared memory
* File mapping

Example:

# 30. Shared Memory

Two processes can map the same physical memory.

```text
Process A
    |
    +------+
           |
           v
      Physical Page
           ^
           |
    +------+
    |
Process B
```

This allows fast IPC.

Shared memory is commonly used when large amounts of data must be exchanged efficiently.

---

# 31. Anonymous Memory

Memory can also be mapped without a file.

For example:

Conceptually:

```text

   |

Anonymous Mapping
   |
   v
Physical Memory
```

This is useful for dynamic memory and shared-memory mechanisms.

# 32. Page Cache

Linux uses memory to cache file data.

This is called the:

```text
Page Cache
```

Simplified read path:

```text

    |
    v

    |
    v

    |
    +-- Miss
           |

           |
```

The page cache is one of the most important Linux performance concepts.

# 33. Page Cache Hit

If file data is already cached:

```text

  |
  v

  |
  v
Data returned
```

This is much faster than reading from disk.

# 36. Physical Memory Management

Linux must track which physical pages are:

```text
Free
Used
Cached
Reclaimable
Reserved
```

The kernel has several memory-management mechanisms for this.

One important allocator is:

```text
Buddy Allocator
```

---

# 37. Buddy Allocator

The buddy allocator manages physical memory in blocks of power-of-two page counts.

Example:

```text
Order 0 -> 1 page
Order 1 -> 2 pages
Order 2 -> 4 pages
Order 3 -> 8 pages
...
```

Conceptually:

```text
Large Block
    |
    +---- Split
          |
          +---- Buddy A
          |
          +---- Buddy B
```

---

# 38. Why Is It Called Buddy?

When a block is split, the resulting blocks are buddies.

Example:

```text
8 pages
   |
   +---------+
   |         |
  4 pages   4 pages
   |         |
   +----+    +----+
   |    |    |    |
  2    2    2    2
```

When adjacent free buddies become available, they can be merged.

---

# 39. Buddy Allocation

Suppose a request requires:

```text
4 pages
```

The allocator finds an appropriate order.

If only an 8-page block is available:

```text
8 pages
   |
   v
Split
   |
   +---- 4 pages
   |
   +---- 4 pages
```

One block is returned.

The other remains available.

---

# 40. Buddy Allocator Limitations

The buddy allocator is good for page-level allocation.

But allocating one page for every tiny kernel object would be inefficient.

For example:

```text
struct object = 64 bytes
```

Allocating an entire 4 KB page is wasteful.

Therefore Linux uses slab-family allocators.

---

# 41. SLAB / SLUB Allocators

Linux provides object allocators such as:

```text
SLAB
SLUB
SLOB
```

Modern general-purpose Linux systems commonly use:

```text
SLUB
```

These allocators efficiently manage small kernel objects.

Conceptually:

```text
Page
 |
 +-- Object
 +-- Object
 +-- Object
 +-- Object
```

---

# 43. kmalloc()

Kernel code commonly uses:

```c
kmalloc()
```

for physically contiguous kernel memory allocations within appropriate limits.

Example:

```c
struct my_data *p;

p = kmalloc(sizeof(*p), GFP_KERNEL);
```

The memory is typically managed through the kernel's slab/slub mechanisms for suitable sizes.

---

# 44. vmalloc()

`vmalloc()` provides virtually contiguous memory.

Important distinction:

```text
kmalloc()
    |
    v
Virtually contiguous
Physically contiguous for the allocated region
```

while:

```text
vmalloc()
    |
    v
Virtually contiguous
Physical pages may be non-contiguous
```

Conceptually:

```text
kmalloc:

VA ---> Page A ---> Page B ---> Page C


vmalloc:

VA ---> Page A
       Page X
       Page Q
```

The virtual addresses appear contiguous to the kernel, while physical pages need not be contiguous for `vmalloc()`.

---

# 45. kmalloc() vs vmalloc()

| Feature             | kmalloc()                                         | vmalloc()                                                   |
| ------------------- | ------------------------------------------------- | ----------------------------------------------------------- |
| Virtual contiguous  | Yes                                               | Yes                                                         |
| Physical contiguous | Yes, for the allocation                           | No requirement                                              |
| Typical use         | Small/medium kernel objects                       | Larger virtually contiguous allocations                     |
| Performance         | Generally faster                                  | More translation overhead                                   |
| DMA suitability     | Often appropriate, subject to device requirements | Often unsuitable for direct DMA without appropriate mapping |

---

# 46. DMA and Physical Contiguity

DMA means:

```text
Direct Memory Access
```

A device can transfer data directly to/from memory without the CPU copying every byte.

Conceptually:

```text
NIC
 |
 | DMA
 v
RAM
```

But device DMA requirements depend on the hardware and IOMMU.

Therefore:

> Never assume that a virtual address is directly usable by a device for DMA.

The kernel uses DMA APIs to obtain the appropriate device-visible address/mapping.

---

# 47. Huge Pages

Normal pages may be relatively small.

Large memory workloads can benefit from larger pages.

Examples include:

```text
Huge Pages
Transparent Huge Pages (THP)
```

Conceptually:

```text
Normal:

4 KB
4 KB
4 KB
4 KB
...

Huge:

2 MB
2 MB
2 MB
...
```

Larger pages can reduce:

* Number of page-table entries
* TLB pressure
* Translation overhead

---

# 48. Transparent Huge Pages

THP attempts to use larger pages automatically where beneficial.

Conceptually:

```text
Application
    |
    v
Normal virtual memory
    |
    v
Kernel attempts larger pages
```

THP can improve performance for some workloads but may have trade-offs.

---

# 49. NUMA

NUMA means:

```text
Non-Uniform Memory Access
```

Large multiprocessor systems can have multiple CPU nodes with local memory.

Example:

```text
+-------------+       +-------------+
| CPU Node 0  |       | CPU Node 1  |
|             |       |             |
| Local RAM 0 |       | Local RAM 1 |
+-------------+       +-------------+
```

CPU 0 accessing its local RAM is generally faster than accessing remote RAM.

---

# 50. NUMA Performance

```text
CPU 0
 |
 +---- Local Memory
 |       Fast
 |
 +---- Remote Memory
         Slower
```

Therefore Linux attempts to maintain good locality.

Important for:

* Databases
* High-performance computing
* Large servers
* Networking
* Storage
* AI/accelerator workloads

---

# 51. Memory Reclaim

Physical RAM is finite.

When memory pressure increases, Linux can reclaim memory.

Conceptually:

```text
Memory Pressure
      |
      v
Reclaim
      |
      +-- Page Cache
      +-- Reclaimable Kernel Memory
      +-- Anonymous Memory handling
```

Some memory can be dropped and reconstructed later.

---

# 52. Swap

Linux can move certain memory pages from RAM to swap storage.

Conceptually:

```text

 |

 v

 |
 v

```

Later:

```text

      |
      v

      |

      |
      v

```

Swap is much slower than RAM.

# 54. Memory Protection

Page-table entries contain protection information.

Conceptually:

```text
Page
 |
 +-- Read
 +-- Write
 +-- Execute
```

Example:

```text
Code:
Read + Execute

Data:
Read + Write

Read-only data:

```

This helps prevent:

```text

Executing data pages
Accessing another process's memory
```

---

# 55. ASLR

ASLR means:

```text
Address Space Layout Randomization
```

Linux can randomize locations of memory regions.

For example:

```text
Without ASLR:

Stack -> predictable location
Library -> predictable location
Heap -> predictable location
```

With ASLR:

```text
Run 1 -> different addresses
Run 2 -> different addresses
Run 3 -> different addresses
```

This makes certain memory-corruption attacks harder.

Multiple processes can share physical pages containing the read-only parts of the same library.

This saves memory.

Security and stability.

Without protection:

```text

             v
```

With protection:

```text

    |
    X
```

The CPU's privilege and memory-protection mechanisms enforce this separation.

# 67. Important Interview Questions

## Q1. What is virtual memory?

A memory abstraction where processes use virtual addresses that are translated to physical memory through page tables.

---

## Q2. What is the MMU?

Hardware that performs virtual-to-physical address translation and enforces memory-access permissions.

---

## Q3. What is a page?

A fixed-size unit of virtual and physical memory management.

---

## Q4. What is a page table?

A data structure used to translate virtual addresses/pages to physical addresses/pages and associated protection information.

---

## Q5. What is the TLB?

A CPU cache containing recently used virtual-to-physical address translations.

---

## Q6. What happens on a TLB miss?

The CPU performs or triggers a page-table walk to obtain the translation. The result may then be cached in the TLB.

---

## Q7. What is a page fault?

An exception generated when a memory access cannot be completed using the current translation/protection state and requires kernel handling.

---

## Q8. Is every page fault an error?

No.

Demand paging, Copy-on-Write, file-backed mappings, and swapping can legitimately generate page faults.

---

## Q9. What is the difference between a minor and major page fault?

A minor fault can be handled without required storage I/O, while a major fault requires storage I/O.

---

## Q10. What is the page cache?

Kernel memory used to cache file contents and reduce storage I/O.

---

## Q11. What is the buddy allocator?

A physical-page allocator that manages blocks of memory in power-of-two orders and can split/merge buddy blocks.

---

## Q12. Why do we need SLUB?

To efficiently allocate and manage small, frequently used kernel objects without allocating an entire page for each object.

---

## Q13. kmalloc() vs vmalloc()?

`kmalloc()` provides virtually contiguous memory that is also physically contiguous for the allocation, while `vmalloc()` provides virtually contiguous memory whose physical pages need not be contiguous.

---

## Q14. What is mmap()?

A mechanism for mapping files or anonymous memory into a process's virtual address space.

---

## Q15. What is NUMA?

A memory architecture where memory-access latency depends on which CPU/node accesses which memory.

---

# 68. Senior-Level Questions

You should be able to explain:

### 1. Why doesn't fork() copy all memory?

Because Linux uses Copy-on-Write.

### 2. Why is TLB needed?

Because page-table translation for every memory access would otherwise be expensive.

### 3. What happens during a page fault?

Explain the CPU → kernel fault handler → page resolution → page-table update → instruction retry flow.

### 4. Why is mmap() useful?

Explain file mapping, shared memory, anonymous mappings, and demand paging.

### 5. Why is page cache important?

Explain how it avoids repeated storage access.

### 6. Buddy vs SLUB?

Explain:

```text
Buddy -> physical page/block allocation

SLUB -> kernel object allocation
```

### 7. kmalloc vs vmalloc?

Explain virtual vs physical contiguity and DMA implications.

### 8. Why do huge pages improve performance?

Fewer pages and page-table entries can reduce TLB pressure.

### 9. Why does NUMA matter?

Remote memory access can have higher latency and lower effective bandwidth.
