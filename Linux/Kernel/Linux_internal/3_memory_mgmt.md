# Chapter 3 – Linux Memory Management

## 1. Why Memory Management Matters
A Linux process does not directly work with physical RAM — instead, it works with **virtual addresses**. Linux and the CPU translate:
```
Virtual Address --> Page Tables --> Physical Address --> RAM
```
This provides: process isolation, efficient memory allocation, virtual memory, memory sharing, demand paging, Copy-on-Write, memory-mapped files, shared libraries, and memory protection.

---

## 2. Virtual Memory
Each process gets its own virtual address space:
```
Process A: Virtual Address Space --> Page Tables --> Physical RAM
Process B: Virtual Address Space --> Page Tables --> Physical RAM
```
So `Process A virtual address 0x1000` and `Process B virtual address 0x1000` can refer to completely different physical memory.

## 3. Why Virtual Memory?
Virtual memory provides several important benefits:
- **Isolation** — one process cannot normally access another process's memory
- **Protection** — pages can be marked Read, Write, or Execute
- **Memory Overcommit** — processes can have virtual memory larger than currently available physical RAM
- **Sharing** — different processes can intentionally map the same physical pages
- **Simpler Programming Model** — each process sees a private address space

---

## 4. Virtual Address vs Physical Address
A virtual address is generated by the CPU while executing a process; a physical address identifies a location in RAM:
```
Virtual Address 0x7fff12345000 --> MMU --> Physical Address 0x12345000
```
The translation is performed using page tables.

## 5. MMU
The **Memory Management Unit (MMU)** is hardware responsible for translating virtual addresses into physical addresses:
```
CPU --Virtual Address--> MMU --Page Table Lookup--> Physical Address --> RAM
```
The Linux kernel manages the page tables, while the CPU/MMU performs the actual translation during memory access.

---

## 6. Pages
Linux manages memory primarily in units called **Pages**. A common page size is 4 KB, but architectures can support other page sizes:
```
Physical RAM: | Page 0 | Page 1 | Page 2 | Page 3 |
```
Memory management operates heavily at page granularity.

## 7. Page Size
If page size = 4096 bytes, then 1 page = 4 KB. A 16 KB allocation requires at least 4 pages if allocated page-by-page. Linux also provides higher-level allocators for smaller objects.

## 8. Page Number and Offset
A virtual address can conceptually be divided into `| Page Number | Offset |`. For a 4 KB page (4096 = 2^12), the offset is the lower 12 bits, and the remaining bits identify the virtual page:
```
Virtual Address: | Virtual Page Number | Offset (12 bits) |
```

---

## 9. Page Table
A page table maps virtual pages to physical pages:
```
Virtual Page       Physical Page
0x1000 ----------> 0xA000
0x2000 ----------> 0xC000
0x3000 ----------> 0x5000
```
So: `Virtual Address --> Page Table --> Physical Page`.

## 10. Page Table Hierarchy
Modern CPUs generally use multi-level page tables:
```
Virtual Address --> Level 4 --> Level 3 --> Level 2 --> Level 1 --> Physical Page
```
The exact number and names of levels depend on architecture and configuration — x86-64, for example, uses a multi-level page-table structure.

## 11. Why Multi-Level Page Tables?
A flat page table could be extremely large. If a process has a huge virtual address space but only uses a small portion, a flat table would waste memory. Multi-level tables let Linux allocate page-table structures only for regions actually used.

---

## 12. TLB
Page-table lookups are expensive if performed for every memory access, so CPUs use a cache called the **TLB** (Translation Lookaside Buffer), which caches recent virtual-to-physical translations:
```
CPU --Virtual Address--> TLB --Hit--> Physical Address
                              --Miss--> Page Table --> Physical Address
```

## 13. TLB Hit
If a virtual page is already in the TLB: `Virtual Address --> TLB --> Physical Address`. This is fast.

## 14. TLB Miss
If translation is not in the TLB: `Virtual Address --> TLB Miss --> Page Table Walk --> Physical Address`. The translation can then be cached in the TLB.

## 15. Why TLB Matters
For every normal memory access, address translation is required. Good TLB locality → better performance; TLB misses → additional translation overhead. This is particularly important in databases, networking, high-performance computing, storage, and large-memory systems.

---

## 16. Page Fault
A page fault occurs when a process accesses a virtual address that requires kernel handling. Not every page fault means an error — for example:
```
Valid demand-paged memory --> Page Fault --> Kernel loads/creates page --> Execution continues
```
This is a **minor/normal memory-management event**, not necessarily a crash.

## 17. Page Fault Example
```c
char *p = malloc(4096);
*p = 'A';
```
The virtual memory may have been reserved/mapped without a physical page being immediately populated. When the CPU accesses the page:
```
Memory Access --> Page not currently mapped as required --> Page Fault --> Kernel
--> Prepare physical page --> Update page table --> Retry instruction
```

## 18. Major vs Minor Page Fault
**Minor Page Fault** — no disk I/O required; the kernel can satisfy the fault using already available memory or mappings.
**Major Page Fault** — disk/storage I/O required:
```
Process --> Page Fault --> Page not in RAM --> Read from storage --> Map page
```
Major page faults are significantly more expensive.

## 19. Demand Paging
Linux can load memory pages only when actually needed — **Demand Paging** — instead of loading everything immediately:
```
Use page --> Fault --> Bring/create page
```
Benefits: faster startup, lower memory usage, efficient memory utilization.

## 20. Copy-on-Write and Memory
COW isn't limited to `fork()` conceptually — it allows multiple mappings to share physical pages until modification:
```
Process A ----+
              v
          Physical Page
              ^
Process B ----+
```
When Process B writes: `Process A ---> Page A`, `Process B ---> Page B`. This reduces unnecessary copying.

---

## 21. Process Address Space
A simplified Linux process address space:
```
High Address
  Kernel Space
  User Stack (grows down)
  mmap() regions
  Heap (grows up)
  BSS / Data / Read-only Data / Text
Low Address
```
The exact layout depends on architecture and configuration.

## 22. Text Segment
The text segment contains executable instructions (machine code). It is normally Readable, Executable, and Not writable — helping prevent accidental modification of program code.

## 23. Data Segment
Initialized global and static variables reside in the data region, e.g.:
```c
int global = 10;
static int count = 5;
```

## 24. BSS
BSS contains zero-initialized or uninitialized global/static variables, e.g.:
```c
int global_array[1000];
static int count;
```
The executable does not need to store all zero bytes explicitly.

## 25. Heap
The heap is used for dynamic memory allocation, e.g. `int *p = malloc(sizeof(int));`
```
Heap --- malloc() --- malloc() --- free()
```
The C library allocator manages user-space allocations; the kernel ultimately provides/manages the underlying virtual memory mappings and physical memory.

## 26. Stack
The stack is used for function calls, local variables, return addresses, function parameters, and saved execution state, e.g.:
```c
void foo() { int x = 10; }
```
```
Stack --- foo() --- x
```
The stack normally grows toward lower addresses on common architectures, but this is architecture-dependent.

---

## 27. mmap()
`mmap()` maps memory or files into a process's virtual address space, e.g. `void *p = mmap(...);`
```
Process Address Space --> mmap() --> Anonymous Memory
                                  --> File Mapping
```
`mmap()` is extremely important in Linux.

## 28. Why mmap() Is Important
`mmap()` is used for memory allocation, shared memory, file mapping, shared libraries, device memory mappings, and efficient I/O:
```
File --mmap()--> Virtual Address Space --> Application accesses memory
```

## 29. Memory-Mapped Files
If `file.dat` is mapped using `mmap()`:
```
Application --> Virtual Memory --> Mapped File --> Filesystem --> Storage
```
The application can access file contents using normal memory accesses.

## 30. Shared Memory
Two processes can map the same physical memory:
```
Process A ----+
              v
         Physical Page
              ^
Process B ----+
```
This allows fast IPC and is commonly used when large amounts of data must be exchanged efficiently.

## 31. Anonymous Memory
Memory can also be mapped without a file, e.g. `mmap(..., MAP_ANONYMOUS, ...);`
```
Process --> Anonymous Mapping --> Physical Memory
```
Useful for dynamic memory and shared-memory mechanisms.

---

## 32. Page Cache
Linux uses memory to cache file data — the **Page Cache**. Simplified read path:
```
Application --> read() --> Page Cache --Hit--> Return data
                                       --Miss--> Filesystem --> Storage
```
The page cache is one of the most important Linux performance concepts.

## 33. Page Cache Hit
If file data is already cached: `read() --> Page Cache --> Data returned`. No storage access is necessary — much faster than reading from disk.

## 34. Page Cache Miss
If data is not cached: `read() --> Page Cache Miss --> Filesystem --> Block Layer --> Storage --> Page Cache --> Application`.

## 35. Page Cache and mmap()
With a file-backed `mmap()`: `Application --> Virtual Address --> Page Fault --> Page Cache --> Filesystem --> Storage`. The page can be populated from the file through the kernel's memory-management/filesystem mechanisms.

---

## 36. Physical Memory Management
Linux must track which physical pages are Free, Used, Cached, Reclaimable, or Reserved. One important allocator: the **Buddy Allocator**.

## 37. Buddy Allocator
Manages physical memory in blocks of power-of-two page counts:
```
Order 0 -> 1 page
Order 1 -> 2 pages
Order 2 -> 4 pages
Order 3 -> 8 pages ...
```
```
Large Block --Split--> Buddy A + Buddy B
```

## 38. Why Is It Called Buddy?
When a block is split, the resulting blocks are buddies:
```
8 pages --> 4 pages + 4 pages --> 2+2 pages, 2+2 pages
```
When adjacent free buddies become available, they can be merged.

## 39. Buddy Allocation
Suppose a request requires 4 pages. If only an 8-page block is available: `8 pages --Split--> 4 pages + 4 pages`. One block is returned; the other remains available.

## 40. Buddy Allocator Limitations
The buddy allocator is good for page-level allocation, but allocating one page for every tiny kernel object (e.g. a 64-byte struct) would be wasteful. Therefore Linux uses slab-family allocators.

---

## 41. SLAB / SLUB Allocators
Linux provides object allocators: SLAB, SLUB, SLOB. Modern general-purpose Linux systems commonly use **SLUB**, which efficiently manages small kernel objects:
```
Page --- Object --- Object --- Object --- Object
```

## 42. Buddy vs SLUB
```
Buddy --> Physical pages, page-level allocation
SLUB  --> Kernel objects, small allocations
```
Relationship: `Physical Memory --> Buddy Allocator --> Pages --> SLUB --> Kernel Objects`

## 43. kmalloc()
Kernel code commonly uses `kmalloc()` for physically contiguous kernel memory allocations within appropriate limits:
```c
struct my_data *p;
p = kmalloc(sizeof(*p), GFP_KERNEL);
```
The memory is typically managed through the kernel's slab/slub mechanisms for suitable sizes.

## 44. vmalloc()
`vmalloc()` provides virtually contiguous memory. Important distinction:
- `kmalloc()` → virtually contiguous, physically contiguous for the allocated region
- `vmalloc()` → virtually contiguous, physical pages may be non-contiguous

```
kmalloc: VA ---> Page A ---> Page B ---> Page C
vmalloc: VA ---> Page A, Page X, Page Q
```
The virtual addresses appear contiguous to the kernel, while physical pages need not be contiguous for `vmalloc()`.

## 45. kmalloc() vs vmalloc()
| Feature | kmalloc() | vmalloc() |
|---|---|---|
| Virtual contiguous | Yes | Yes |
| Physical contiguous | Yes, for the allocation | No requirement |
| Typical use | Small/medium kernel objects | Larger virtually contiguous allocations |
| Performance | Generally faster | More translation overhead |
| DMA suitability | Often appropriate, subject to device requirements | Often unsuitable for direct DMA without appropriate mapping |

## 46. DMA and Physical Contiguity
DMA means **Direct Memory Access** — a device can transfer data directly to/from memory without the CPU copying every byte:
```
NIC --DMA--> RAM
```
Device DMA requirements depend on the hardware and IOMMU — never assume a virtual address is directly usable by a device for DMA. The kernel uses DMA APIs to obtain the appropriate device-visible address/mapping.

---

## 47. Huge Pages
Normal pages may be relatively small; large memory workloads can benefit from larger pages (Huge Pages, Transparent Huge Pages/THP):
```
Normal: 4 KB, 4 KB, 4 KB, 4 KB...
Huge:   2 MB, 2 MB, 2 MB...
```
Larger pages can reduce the number of page-table entries, TLB pressure, and translation overhead.

## 48. Transparent Huge Pages
THP attempts to use larger pages automatically where beneficial:
```
Application --> Normal virtual memory --> Kernel attempts larger pages
```
THP can improve performance for some workloads but may have trade-offs.

## 49. NUMA
NUMA means **Non-Uniform Memory Access**. Large multiprocessor systems can have multiple CPU nodes with local memory:
```
CPU Node 0 (Local RAM 0)     CPU Node 1 (Local RAM 1)
```
CPU 0 accessing its local RAM is generally faster than accessing remote RAM.

## 50. NUMA Performance
```
CPU 0 --> Local Memory (Fast)
       --> Remote Memory (Slower)
```
Linux attempts to maintain good locality. Important for databases, HPC, large servers, networking, storage, and AI/accelerator workloads.

---

## 51. Memory Reclaim
Physical RAM is finite; when memory pressure increases, Linux can reclaim memory:
```
Memory Pressure --> Reclaim
   +-- Page Cache
   +-- Reclaimable Kernel Memory
   +-- Anonymous Memory handling
```
Some memory can be dropped and reconstructed later.

## 52. Swap
Linux can move certain memory pages from RAM to swap storage:
```
RAM --Memory Pressure--> Swap --> Storage
```
Later: `Process accesses page --> Page Fault --> Read page from swap --> RAM`. Swap is much slower than RAM.

## 53. Out-Of-Memory Condition
If Linux cannot satisfy memory demands after reclaim and other mechanisms, the system can enter an **Out-Of-Memory** condition. The kernel's OOM mechanisms can select processes for termination:
```
Memory Pressure --> Reclaim --> Still insufficient --> OOM Handling --> Terminate selected process
```

---

## 54. Memory Protection
Page-table entries contain protection information: Read, Write, Execute. Example:
- Code: Read + Execute
- Data: Read + Write
- Read-only data: Read

This helps prevent writing executable code, executing data pages, and accessing another process's memory.

## 55. ASLR
ASLR means **Address Space Layout Randomization**. Linux can randomize locations of memory regions. Without ASLR, stack/library/heap locations are predictable across runs; with ASLR, each run gets different addresses. This makes certain memory-corruption attacks harder.

## 56. Memory-Mapped Shared Libraries
When an application uses a shared library (`libc.so`), the library can be mapped into the process address space:
```
Process --- Code --- Heap --- Stack --- libc.so --- Other Libraries
```
Multiple processes can share physical pages containing the read-only parts of the same library, saving memory.

---

## 57. Complete Memory Access Flow
For `x = *ptr;`:
```
CPU --Virtual Address--> TLB --Hit--> Physical Address
                              --Miss--> Page Table Walk --> Physical Address --> RAM
```
If the required mapping/page is unavailable:
```
Page Fault --> Kernel --> Resolve mapping/page --> Update page table --> Retry instruction
```

## 58. Complete malloc() Mental Model
For `malloc(100);`, the application calls the C library allocator:
```
Application --> malloc() --> C Library Allocator
   +-- Existing heap memory
   +-- mmap()/brk() when more memory is needed
   --> Virtual Memory --> Kernel Memory Management
```
Important: `malloc()` is not itself a direct system call — the allocator may obtain memory from the kernel using mechanisms such as `brk()`/`mmap()`.

## 59. malloc() vs mmap()
The C allocator may use `brk()` and `mmap()` depending on allocation size and allocator implementation:
```
malloc() --- Existing allocator arena --- brk() --- mmap()
```
The exact behavior depends on the C library allocator and configuration.

---

## 60. Page Fault – Interview Flow
If asked *"What happens during a page fault?"*:
```
CPU accesses virtual address --> Translation/permission check --> Fault detected
--> CPU enters kernel fault handler --> Kernel determines fault reason
   +-- Valid demand page?
   +-- COW?
   +-- File-backed page?
   +-- Swap?
   +-- Invalid access?
--> Resolve if possible --> Update page tables --> Retry instruction
```
If the access is invalid: `Kernel --> SIGSEGV` may be delivered to the process.

## 61. Copy-on-Write – Interview Flow
If asked *"Explain COW after fork()"*:
```
fork() --> Parent + Child --> Share physical pages --> Pages protected for COW
--> Child writes --> Page Fault --> Allocate new page --> Copy data
--> Update child page table --> Retry write
```

## 62. mmap() – Interview Flow
If asked *"What happens when mmap() is used?"*:
```
Application --> mmap() --> Kernel --> Create virtual-memory mapping
--> VMA/page-table setup as required --> Return virtual address
```
Physical pages may not be populated immediately. Later: `Application accesses address --> Page Fault --> Kernel populates required page`. For a file-backed mapping, Page Cache/Filesystem can participate in obtaining the data.

## 63. Page Cache – Interview Flow
If asked *"What happens when a process reads a file?"*:
```
read() --> VFS --> Filesystem --> Page Cache --Hit--> Return data
                                             --Miss--> Block Layer --> Storage --> Page Cache --> Application
```
This flow becomes extremely important when studying VFS and storage internals.

---

## 64. Important Memory Structures
Know these names: `mm_struct`, `vm_area_struct`, Page, page tables, PTE, PMD, PUD, PGD. The exact page-table level names depend on architecture/configuration:
```
task_struct --> mm_struct
                  +-- VMAs
                  +-- Page-table root --> Page Tables --> Physical Pages
```

## 65. Kernel Memory vs User Memory
**User Memory** — process-specific, user virtual address space.
**Kernel Memory** — kernel code, kernel data, kernel allocations, kernel stacks.

A user process cannot normally directly access arbitrary kernel memory.

## 66. Why Kernel and User Memory Are Separated
Security and stability. Without protection, an application could overwrite kernel memory, causing system corruption. With protection, the application cannot touch kernel memory. The CPU's privilege and memory-protection mechanisms enforce this separation.

---

## 67. Important Interview Questions

**Q1. What is virtual memory?**
A memory abstraction where processes use virtual addresses that are translated to physical memory through page tables.

**Q2. What is the MMU?**
Hardware that performs virtual-to-physical address translation and enforces memory-access permissions.

**Q3. What is a page?**
A fixed-size unit of virtual and physical memory management.

**Q4. What is a page table?**
A data structure used to translate virtual addresses/pages to physical addresses/pages and associated protection information.

**Q5. What is the TLB?**
A CPU cache containing recently used virtual-to-physical address translations.

**Q6. What happens on a TLB miss?**
The CPU performs or triggers a page-table walk to obtain the translation. The result may then be cached in the TLB.

**Q7. What is a page fault?**
An exception generated when a memory access cannot be completed using the current translation/protection state and requires kernel handling.

**Q8. Is every page fault an error?**
No — demand paging, Copy-on-Write, file-backed mappings, and swapping can legitimately generate page faults.

**Q9. What is the difference between a minor and major page fault?**
A minor fault can be handled without required storage I/O, while a major fault requires storage I/O.

**Q10. What is the page cache?**
Kernel memory used to cache file contents and reduce storage I/O.

**Q11. What is the buddy allocator?**
A physical-page allocator that manages blocks of memory in power-of-two orders and can split/merge buddy blocks.

**Q12. Why do we need SLUB?**
To efficiently allocate and manage small, frequently used kernel objects without allocating an entire page for each object.

**Q13. kmalloc() vs vmalloc()?**
`kmalloc()` provides virtually contiguous memory that is also physically contiguous for the allocation, while `vmalloc()` provides virtually contiguous memory whose physical pages need not be contiguous.

**Q14. What is mmap()?**
A mechanism for mapping files or anonymous memory into a process's virtual address space.

**Q15. What is NUMA?**
A memory architecture where memory-access latency depends on which CPU/node accesses which memory.

---

## 68. Senior-Level Questions
You should be able to explain:
1. **Why doesn't fork() copy all memory?** Because Linux uses Copy-on-Write.
2. **Why is TLB needed?** Because page-table translation for every memory access would otherwise be expensive.
3. **What happens during a page fault?** Explain the CPU → kernel fault handler → page resolution → page-table update → instruction retry flow.
4. **Why is mmap() useful?** Explain file mapping, shared memory, anonymous mappings, and demand paging.
5. **Why is page cache important?** Explain how it avoids repeated storage access.
6. **Buddy vs SLUB?** `Buddy -> physical page/block allocation`; `SLUB -> kernel object allocation`.
7. **kmalloc vs vmalloc?** Explain virtual vs physical contiguity and DMA implications.
8. **Why do huge pages improve performance?** Fewer pages and page-table entries can reduce TLB pressure.
9. **Why does NUMA matter?** Remote memory access can have higher latency and lower effective bandwidth.

## 69. Whiteboard Mental Model
The most important memory flow:
```
                 Process
                    |
               mm_struct
                    |
             Virtual Address
                    |
                   TLB
                 /     \
              Hit       Miss
               |          |
               |      Page Tables
               |          |
               +----------+
                    |
             Physical Address
                    |
                   RAM
```
If the required page is unavailable:
```
Virtual Address --> Page Fault --> Kernel --> Resolve Page --> Update Page Table --> Retry Instruction
```

## 70. Memory Allocation Mental Model
```
User Space --> malloc() --> C Library Allocator
   +-- Existing memory
   +-- brk()
   +-- mmap()
   --> Virtual Memory --> Kernel Memory Management
                             +-- Page Allocator
                             +-- Buddy
                             +-- Page Cache
                             +-- Reclaim
                             +-- Swap
```
Kernel allocation:
```
Kernel --- kmalloc() --> SLUB
       --- vmalloc() --> Virtually contiguous memory
```
